AI 네이티브 팀 개발 구조 · 개인 프로젝트 · 공개 · MIT · 2026

병목AI로 코드 작성이 빨라진 팀에서는 병목이 다른 단계로 옮겨 갑니다. 리뷰를 기다리는 PR이 쌓입니다. 두 사람의 AI가 같은 영역을 따로 작업하기도 하고 레포 사이의 API·이벤트·스키마가 알림 없이 깨지기도 합니다. 이 레포는 세 병목마다 대응 장치를 설계해 공개했습니다.

설계 먼저일의 크기에 따라 절차를 나눕니다. T0(한 문장으로 설명되는 변경)는 이슈와 PR, T1(여러 파일, 접근법이 열려 있음)은 PR 본문 맨 위에 AI 계획, T2(여러 모듈·레포, 계약 변경, 하루 이상)는 1쪽 설계 PR을 먼저 머지합니다. 설계를 먼저 머지하는 것은 팀 절차입니다. design-check는 설계 링크가 없는 큰 PR에 알림을 답니다. 허브의 팀 작업 보드는 30분마다 등록한 레포의 설계와 열린 PR을 모읍니다. 보드에는 설계에 선언한 영역과 열린 PR만 보입니다. 보드 집계는 LLM 없이 결정적으로 동작해 토큰을 쓰지 않습니다. 작업 전에 /check-overlap(수백 토큰)이나 make overlap으로 같은 영역(src/auth/** 같은 경로 글롭)을 누가 작업 중인지 확인합니다. 겹치면 담당자와 대화해 합치거나 영역을 나누거나 순서를 정합니다.

계약 먼저여러 레포가 함께 일할 때 비용이 가장 큰 사고는 API·이벤트·스키마가 알림 없이 깨지는 경우입니다. 계약 PR을 구현 PR보다 먼저 머지합니다. contract-check 워크플로가 계약 파일이 바뀐 PR에 댓글을 답니다. 깨지는 변경을 자동으로 찾는 대상은 OpenAPI(oasdiff)와 protobuf(buf)뿐입니다. 깨지는 변경은 breaking-change 라벨이 있어야 통과합니다. 라벨을 붙이기 전에 소비자와 전환 계획을 합의하는 것은 팀 규칙입니다.

리뷰리뷰 시간은 늘릴 수 없으므로 유입량을 조절합니다. pr-checks의 Review load가 1인당 리뷰 대기 PR 상한(MAX_OPEN_PRS_PER_AUTHOR, 기본 3)을 넘으면 알립니다. 차단하지는 않습니다. PR 템플릿의 Reviewer guide에는 먼저 볼 곳, 확인한 것, 확인 못 한 것을 적습니다. AI 리뷰는 참고용이고 승인은 사람 CODEOWNER가 합니다. 같은 지적이 두 번 나오면 규칙으로 바꿉니다. 주간 유지보수 리포트(AI_BACKEND를 켜면 매주 월요일, 또는 make ai-maintenance)가 review-comments.sh로 지난주 리뷰 댓글을 모으고(수집은 토큰 0) 2개 이상 PR에서 나온 주제마다 수정 방법을 이슈로 제안합니다. 린트 규칙이나 테스트가 먼저이고 AGENTS.md 한 줄은 그다음입니다. 반영은 사람이 PR로 합니다. 핵심 팀 스킬은 긍정·부정 평가 케이스(design-for-cross-area-work, no-design-for-typo)로 테스트합니다.

기반모든 장치는 같은 기반 위에서 동작합니다. AI 도구 5종(Claude Code, GitHub Copilot, Cursor, OpenAI Codex, Gemini)의 도구별 파일이 AGENTS.md(약 60줄)를 먼저 읽게 합니다. 내 자리에서도 CI가 실행하는 검사(make check)를 그대로 실행합니다. 에이전트 작업의 사람 판단은 두 곳으로 ai:ready 부여와 CODEOWNER 승인입니다. Claude Code 훅은 보호 경로 수정, main 커밋, 공유 브랜치 강제 푸시를 막고, 다른 도구는 pre-commit과 룰셋이 막습니다. agent-approval-check는 Claude·Copilot 커밋이 든 PR의 사람 승인을 한 번 더 확인합니다. 허브 레포 하나에서 규칙은 템플릿(make new-repo)으로, 훅과 스킬은 플러그인 마켓플레이스(claude plugin update)로 여러 레포에 배포합니다. 워크플로는 23개, 스킬 11개, 서브에이전트 5개입니다.

화면의 그래프는 개념도입니다. 레인 수, A·B, svc-a·web, src/auth/**는 예시입니다. 도입 사례나 측정한 효과가 아니라 설계해 공개한 참조 구현입니다.
